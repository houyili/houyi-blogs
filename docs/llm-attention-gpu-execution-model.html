从 LLM Attention 讲透 GPU 执行模型

这篇不从 GPU 术语表开始，而从 decode attention 的热循环开始：QK -> softmax -> PV。目标是解释为什么 HBM、L2、shared memory、register、SM、warp、CUDA Core、Tensor Core、SFU、warp scheduler 这些层级不是装饰，以及它们如何决定 RoPE / KV cache kernel 的工程代价。

1. 为什么 LLM 推理问题会变成 GPU 执行问题

Transformer 里 attention 的数学写法很干净：scores = QK^T，P = softmax(scores)，O = PV。但在 GPU 上，它不是一个抽象公式，而是一串数据搬运、tile 复用、矩阵乘、标量控制、同步和输出累加。

Prefill 阶段通常有较长 query 序列，batch 和 token 维度能形成较大的 GEMM，问题更像“如何把 Tensor Core 喂满”。Decode 阶段每次新增 token 少，历史 KV cache 长，attention 更像“反复从 KV cache 里拿 tile，做一个小 query 对很多历史 key/value 的热循环”。这也是为什么同样叫 attention，prefill 和 decode 的瓶颈形态很不一样。

decode attention tile: load KV tile from HBM/L2 -> stage in shared memory -> QK MMA on Tensor Core -> online softmax on CUDA Core/SFU -> PV MMA on Tensor Core -> update output accumulator

所以“HBM 带宽够不够”或“峰值 FLOPs 够不够”都只是第一层问题。真正落到 kernel 时，还要问：KV tile 是否能在 shared memory 里复用？寄存器里有多少 live fragment？warp scheduler 有没有 ready warp 可以发射？Tensor Core 在等数据，还是 CUDA Core/SFU 在做标量阶段？这些问题由 CUDA 的 thread/block/SM 层级和 memory hierarchy 共同决定。[CUDA-SM][CUDA-Mem]

2. GPU 的层级不是装饰：每一层回答不同问题

对 LLM inference 来说，GPU memory hierarchy 不是简单的“越近越快”。它更像一份执行合约：什么数据大到只能放 HBM，什么数据要进入 L2 被多个 SM 机会性复用，什么 tile 能被一个 thread block 放进 shared memory 协作使用，什么 fragment 必须留在每个 thread 的 register 里。

HBM

放权重和 KV cache。容量大、带宽高，但 off-chip memory latency 通常远高于片上依赖；CUDA Guide 明确把 off-chip latency 描述为数百周期量级。[CUDA-Lat]

L2

跨 SM 的缓存层。paged KV、sparse top-k gather、batch 间是否读相近页面，会影响 L2 命中与合并访问，但 kernel 不能像 shared memory 那样精确声明“这块 tile 给我复用两次”。

Shared Memory

thread block 内共享，生命周期等于 block。它通常是 attention tile 的核心复用层：KV 从 HBM/L2 进来后，QK 和 PV 都想从这里读。

Register

每个线程私有，保存 MMA fragment、softmax 的 max/sum、输出 accumulator、地址/scale 等临时变量。寄存器越多，单 SM 可同时驻留的 warp/block 可能越少，occupancy 下降。[CUDA-Occ]

Barrier 与覆盖

shared memory 可以复用，也可以覆盖，但覆盖不是免费动作。若旧表示仍被 QK consumer 读取，另一个 warp 就不能把同一地址改写成 V 表示给 PV 读，这时需要同步保证生产者/消费者顺序。[CUDA-Sync]

3. SM 是什么：Tensor Core 和 CUDA Core 的上一级执行单元

一个 NVIDIA GPU 由多个 Streaming Multiprocessor，也就是 SM，组成。CUDA kernel 启动后，grid 中的 thread blocks 会被分发到有执行容量的 SM 上；每个 block 的线程在一个 SM 上并发执行，多个 blocks 也可以同时驻留在同一个 SM 上。[CUDA-SM]

直接回答：从硬件层级上，可以说 SM 是 Tensor Core、CUDA Core/SFU、LD/ST 单元、warp scheduler、register file、shared memory/L1 的上一级执行单元。Tensor Core 和 CUDA Core 不是彼此的上下级；它们是同一个 SM 里的不同功能单元，被 warp scheduler 发射的不同指令占用。

这一区分对 LLM kernel 很要命。QK/PV 是 dense matrix multiply accumulate，适合 Tensor Core；RoPE、inverse RoPE、relative rotate、mask、index decode、softmax 的 exp/scale、online softmax 的 max/sum 更新，主要走 CUDA Core/SFU/LD-ST 路径。Tensor Core 的理论 TFLOPs 不能直接支付这些标量和控制工作。CUDA C++ Programming Guide 在 SM 架构列表中把 Tensor Cores 和 warp schedulers列为 SM 组成部分；Hopper 文档进一步给出 H100 SM 的寄存器和 shared memory 容量。[CUDA-TC][Hopper-SM]

4. warp、thread、block：GPU 到底怎么并行

CUDA 的编程视角是 thread，但硬件调度基本单位是 warp。一个 thread block 包含一组 threads，这些 threads 会被划分成 warps；NVIDIA 文档描述 warp 由连续 thread ID 组成，通常 32 个 thread 一组。block 被分发到一个 SM 上执行，SM 内可以同时驻留多个 block 和多个 warp。[CUDA-Warp]

warp 是多线程的吗？是。warp 是硬件调度的一组 threads；一条 warp 指令会发给该 warp 的 active threads。你写的是很多 CUDA threads，硬件按 warp 组织它们、调度它们、隐藏延迟。

SM 内并行和 SM 间并行也要分开看。SM 内：同一 SM 上多个 resident warps 交错执行，部分 warp 发 MMA，部分 warp 做 load/store，部分 warp 做 softmax 或地址计算；但同一个 thread block 内 shared memory 读写需要通过 __syncthreads() 或更细粒度 barrier 保证顺序。SM 间：不同 blocks 被分发到不同 SM，默认彼此独立，不能用普通 __syncthreads() 跨 SM 同步；跨 block 协调通常依赖 global memory、新 kernel 边界，或 Hopper 的 cluster / distributed shared memory 等特殊机制。[CUDA-Block][Hopper-TMA]

5. 把 LLM Attention 映射到 GPU 流水

现在把术语放回 decode attention。一个常见 tile 流水是：KV cache 在 HBM；请求进入 SM 前可能经过 L2；thread block 把一个 KV tile 搬进 shared memory；QK 通过 Tensor Core 做 MMA；softmax 的 max/sum/exp/scale 走 CUDA Core/SFU；PV 再走 Tensor Core，把 probability tile 乘 value tile，更新输出 accumulator。

DSV4 reference code 可以作为很好的具体例子：inference/model.py 里对 q 和 kv 的 RoPE slice 先做 apply_rotary_emb，进入 sparse_attn；输出 o 的 RoPE slice 再做 inverse=True。inference/kernel.py 中 kv_shared gather 后先作为 K 参与 T.gemm(q_shared, kv_shared, ... transpose_B=True)，随后同一份 kv_shared 又作为 V 参与 T.gemm(acc_s_cast, kv_shared, acc_o)。换句话说，同一份 kv_shared 连续喂两个 GEMM。[DSV4-Code-M][DSV4-Code-K] 

# simplified from the DSV4 reference sparse attention kernel
kv_shared = gather(kv_cache, idxs)           # one shared tile
acc_s     = q_shared @ kv_shared.T          # QK: kv_shared as K
p         = online_softmax(acc_s)           # max/sum/rescale logic
acc_o    += p @ kv_shared                   # PV: same kv_shared as V

这个复用是当前设计的工程红利：同一份 shared tile 被两个 GEMM 连续消费，中间不需要把 tile 从一种表示改成另一种表示。CUTLASS 的 GEMM 文档也描述了典型高性能 GEMM 的层级：threadblock 级 shared tile、warp 级 fragment、register accumulator，以及通过 pipeline/double buffering 把搬运和计算重叠。[CUTLASS-GEMM][CUTLASS-Pipe]

6. 为什么要区分 Tensor Core 和 CUDA Core

这点是理解“多一层 RoPE 为什么不必然免费”的核心。Tensor Core 擅长规则的矩阵乘累加，吞吐极高，但它吃的是已经排好布局的矩阵 fragment。RoPE、inverse RoPE、relative rotate、top-k gather 的地址计算、paged KV 的 page table lookup、mask、softmax exp、rescale old accumulator，都不是同一类 workload。

例如把 K 的 RoPE 放进 decode 内循环：你也许不增加 HBM 字节数，因为还是读一个 K；也可以选择在寄存器 fragment 中边读边旋转，避免存两份。但 QK MMA 需要的是 rotated K fragment，这意味着 Tensor Core 要等 K-ready。再比如 DSV4 value own-position inverse：QK 消费的是 K 表示，PV 消费的是 V 表示；如果它们共享同一块 kv_shared，中间的 value transform 就不是“顺手算一下”，而是改变 shared tile 的语义，产生 producer/consumer 依赖。

7. memory-bound 的正确理解：roofline 和 critical path 是两件事

说 decode attention memory-bound，通常是从 roofline 视角：HBM 搬运 KV cache 的字节数相对计算量很大，整体吞吐容易受 HBM 带宽约束。但 kernel 的执行时间不是只由总字节数决定。一个操作如果插在 QK 和 PV 之间，并且 PV 必须等待它产出新表示，那么它会拉长 tile 的 critical path，即使 HBM 字节数没有增加。

Hopper 的 TMA 和 CUDA 的 async copy 能让 global-to-shared 搬运与 SM 内计算重叠；CUTLASS 的 pipeline 也会给 shared tile 和 register fragment 做多级 buffering。[Hopper-TMA][CUTLASS-Pipe] 但隐藏成立有条件：当前工作必须与被等待的数据无依赖，并且有足够 resident warps 或独立指令可发射。CUDA Guide 对 latency hiding 的描述也强调，warp scheduler 需要 ready instructions；同步点会让越来越多 warp 等待，从而降低利用率。[CUDA-Sched]

不是说现场旋转一定慢。如果旋转可以放在独立 pipeline stage、用额外 buffer 避免覆盖 hazard、或者 tile 形状让 CUDA Core/SFU 工作被其他 tile 的 load/MMA 吃掉，它可能很便宜。本文的结论更窄：当旋转改变当前 tile 被下游 GEMM 消费前的表示，并且处在 producer/consumer 硬依赖链上，它就不能仅凭“decode memory-bound”被判定为免费。

8. 回到 RoPE/KV Cache：这套 GPU 模型如何解释原问题

现在把两个讨论合并。K 现场 RoPE 和 DSV4 own-position value inverse / relative rotate 的相似性在于：它们都把位置变换搬进 per-KV tile 热循环，区别只是插入点不同。

K 现场 RoPE

插在 load kv tile 与 QK MMA 之间。QK 需要 rotated K，所以 K-ready 是 QK 的前置条件。代价主要是 position metadata、CUDA Core/SFU 旋转、fragment/register 或 shared tile 处理，以及 Tensor Core feed 的等待风险。

own-position value inverse

插在 QK/softmax 与 PV MMA 之间。如果同一份 kv_shared 先当 K 后当 V，而 V 需要另一种表示，那么就需要 transform 阶段和同步，或改成多 buffer/重读/重排 kernel。

方案 插入位置 主要硬件资源 能否隐藏 主要风险
pre-RoPE K cache cache 写入侧 prefill/decode 写 cache 前的 CUDA Core/SFU 或向量路径 decode 热循环直接读 ready K，最容易隐藏 cache 数值已经绑定位置，改变位置编码策略要重算或重写路径
raw-K decode 现场 RoPE QK 前 CUDA Core/SFU、position metadata、register/shared、LD/ST 可通过 fragment-level transform、pipeline 优化部分隐藏；但 QK 消费 rotated K，存在前置依赖 position 读取、寄存器 live range、shared tile 处理、Tensor Core feed 等待
DSV4 Q-position inverse PV 后输出侧 CUDA Core/SFU，对最终 o[..., -rd:] 一次 inverse 不改 kv_shared，不阻塞 QK/PV 的 shared tile 复用 这是特定算法选择；本文只说明其工程位置便宜
own-position V inverse / relative rotate QK/softmax 与 PV 中间 CUDA Core/SFU、shared read/write、register、barrier 如果原地改写同一 kv_shared，很难完全隐藏；可用双 buffer、重读、重排 kernel 换别的代价 tile 表示相位改变、consumer/producer 同步、shared bandwidth、occupancy、PV Tensor Core 等待

最后的判断可以压成一句话：不是不能写这种 kernel，也不是“寄存器一定翻倍”这种粗糙结论。真正的工程代价是，位置变换从 cache 写入侧或输出侧搬进 per-KV tile 热循环后，会改变 tile representation、shared memory phase、barrier 需求、register pressure 和 Tensor Core feed。算法数学上可行，不等于在 GPU 流水上免费。
