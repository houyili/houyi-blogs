K 现场 RoPE 与 DSV4 Value 旋转：为什么“算力够”仍可能拖慢 Decode Attention

这篇只讨论工程执行，不争论模型语义。核心问题是：位置变换如果从 cache 写入侧或输出侧，被搬进 per-KV tile 的热循环，它会占用哪些 GPU 资源，卡住哪条依赖链，以及为什么 memory-bound 并不意味着这些工作可以无代价消失。

1. 问题复述：两个问题是一张账本

K 现场 RoPE 和 DSV4 value own-position inverse / relative rotate 的共同点，不是“都多做一点旋转”这么浅，而是它们都把原本在 cache 写入侧 或 输出向量侧 的位置变换，移动到了 attention kernel 的 per-KV tile 路径里。

K 现场 RoPE

标准路径写 cache 前就把 key 变成 ready-to-dot 的 R(t)K_raw。替代路径存 K_raw，decode 时按每个历史 token 的位置 t 现场旋转，再做 QK。

Kcache,t=R(t)Kraw,t,sq,t=(R(q)Qq)⊤Kcache,tK_{\mathrm{cache},t}=R(t)K_{\mathrm{raw},t},\qquad s_{q,t}=\bigl(R(q)Q_q\bigr)^\top K_{\mathrm{cache},t}Kcache,t​=R(t)Kraw,t​,sq,t​=(R(q)Qq​)⊤Kcache,t​

DSV4 Value own-position inverse

DSV4 的 KV entry 同时是 key 和 value，partial RoPE 作用在最后 64 维。当前实现是 attention 输出后按 query 位置做一次 inverse；替代方案则是每个 value 按自己的位置或相对位置变换后再进 PV。

oq=R(−q)∑tαq,t R(t)ct=∑tαq,t R(t−q)cto_q=R(-q)\sum_t \alpha_{q,t}\,R(t)c_t=\sum_t\alpha_{q,t}\,R(t-q)c_toq​=R(−q)t∑​αq,t​R(t)ct​=t∑​αq,t​R(t−q)ct​

如果只看数学，K 现场 RoPE 可以等价于 pre-RoPE cache；value own-position inverse 则是另一个模型语义选择。本文不评判语义，只看工程：这些旋转放在 QK/PV 热循环的哪个位置，以及它们是否破坏 tile 复用。RoFormer 论文给出了 RoPE 的基本相对位置内积形式。[RoPE]

本文推导边界：后文的 FLOP、shared traffic 和延迟图是估算模型，用来定位代价来源，不等价于某张卡上的 Nsight profile。所有“会慢/可能慢”的说法都限定在当前 DSV4 sparse attention 形态和常见 IO-aware tile kernel 组织下。

2. GPU 执行模型：memory-bound 不是只有 HBM

CUDA kernel 的基本单位是 thread block。一个 block 被调度到 SM 上，block 内线程可以共享 shared memory，并通过 __syncthreads() 这类同步点协调访问。CUDA Programming Guide 明确说明 shared memory 对 block 内线程可见、生命周期随 block，__syncthreads() 是 block 级 barrier。[CUDA-Mem][CUDA-Sync]

一个 attention tile 在 GPU 上大致会经过 HBM/L2、shared memory、register、CUDA Core/SFU、Tensor Core、warp scheduler 这些层级。Hopper Tuning Guide 给出 H100 的片上资源轮廓：每 SM shared memory 最高 228 KB，L2 50 MB，HBM3 最高约 3 TB/s；H100 产品规格页还列出 3.35 TB/s 或 3.9 TB/s 的 GPU memory bandwidth，以及高得多的 Tensor Core 峰值。[Hopper][H100]

HBM/L2

负责把 KV cache tile 搬到 SM 附近。decode attention 通常对这层敏感。

SMEM/Register

负责 tile 复用。额外 shared read/write 或 register fragment 会影响 occupancy 和 bank conflict。

CUDA/Tensor Core

Tensor Core 跑 GEMM，CUDA Core/SFU 跑 softmax、exp、地址计算、RoPE 旋转等非 MMA 工作。

FlashAttention 的 IO-aware 分析说明 attention 性能要数 HBM 与片上 SRAM 之间的读写，而不是只数 FLOPs；CUTLASS 的 GEMM 文档也强调高性能 GEMM 依赖分层 tiling、shared memory/register reuse 和 pipelining。[FA-IO][FA-Softmax][CUTLASS][CUTLASS-Pipe]

3. DSV4 当前热循环：一份 kv_shared 连续喂两个 GEMM

DeepSeek-V4 报告说 CSA/HCA 使用 shared Key-Value MQA：compressed KV entry 在 core attention 中同时作为 key 和 value；partial RoPE 作用在 query、KV entry 和 core attention output 的最后 64 维。[DSV4][DSV4-KV]

本地 reference implementation 也很直接：inference/model.py 中 q 和 kv 先分别 apply_rotary_emb，然后进入 sparse_attn，输出 o 的 RoPE slice 再 inverse=True。[Code-QKVO] 在 inference/kernel.py 中，kv_shared 被 gather 之后先用于 T.gemm(q_shared, kv_shared, ... transpose_B=True)，随后同一份 kv_shared 被 T.gemm(acc_s_cast, kv_shared, acc_o) 用作 value。[Code-Kernel][vLLM] 

for each topk tile:
    idxs       = topk_idxs[by, bx, tile]
    kv_shared  = gather(kv_cache, idxs)          # one loaded representation
    acc_s      = q_shared @ kv_shared.T          # QK, kv_shared as K
    p          = online_softmax_update(acc_s)
    acc_o     += p @ kv_shared                   # PV, same kv_shared as V

4. 为什么现场旋转不是“免费”：它插进 critical path

K 现场 RoPE 与 value own-position inverse 的第一层代价是 CUDA Core/SFU 上的旋转计算。但更关键的是位置：如果旋转发生在 QK/PV 中间，PV 的 Tensor Core 不能在 value representation 准备好之前启动。

Tcurrent≈Tload+TQK+Tsoftmax+TPV,Twith transform≈Tload+TQK+Tsoftmax+Ttransform+TPV+Tsync.\begin{aligned}T_{\mathrm{current}} &\approx T_{\mathrm{load}} + T_{\mathrm{QK}} + T_{\mathrm{softmax}} + T_{\mathrm{PV}},\\ T_{\mathrm{with\ transform}} &\approx T_{\mathrm{load}} + T_{\mathrm{QK}} + T_{\mathrm{softmax}} + T_{\mathrm{transform}} + T_{\mathrm{PV}} + T_{\mathrm{sync}}.\end{aligned}Tcurrent​Twith transform​​≈Tload​+TQK​+Tsoftmax​+TPV​,≈Tload​+TQK​+Tsoftmax​+Ttransform​+TPV​+Tsync​.​

上式不是性能模型的全部，但它抓住了 critical path 的本质：T_transform 如果依赖 QK 读完旧表示，又被 PV 等待，那么它就不是能被 HBM latency 完全覆盖的后台工作。Hopper 的 TMA/async copy 能帮助 global-to-shared 的搬运与计算重叠，但数据被消费前仍需要同步对象保证 ready。[CUDA-Async][Hopper]

K 现场 RoPE 的位置

如果 cache 存 raw K，QK GEMM 前需要把 raw K fragment 变成 R(t)K。这可能在 shared tile 上做，也可能在寄存器 fragment 中做；二者都插在 load 和 QK 之间。

V 现场 inverse 的位置

DSV4 当前 Q-position inverse 是输出侧一次处理；own-position inverse 若不多存一份，则要在 QK 后、PV 前把同一份 tile 从 K 表示改成 V 表示。

4.1 一个粗账本：为什么小计算也能碍事

以 DSV4 的 head_dim=512、rope_head_dim=64、本地 sparse kernel 的 block=64 为例，如果对一个 KV tile 的 RoPE 维做 value own-position inverse，需要处理 64×64=4096 个 BF16 元素，也就是 2048 个二维旋转 pair。[DSV4-Config][Code-Kernel]

pairs/tile=64×(64/2)=2048,scalar ops/tile≈2048×(4 mul+2 add)≈12,288,shared traffic/tile≈4096×2 bytes×2 (read+write)≈16 KB.\begin{aligned}\text{pairs/tile}&=64\times(64/2)=2048,\\ \text{scalar ops/tile}&\approx 2048\times(4\ \mathrm{mul}+2\ \mathrm{add})\approx 12{,}288,\\ \text{shared traffic/tile}&\approx 4096\times2\ \mathrm{bytes}\times2\ \mathrm{(read+write)}\approx16\ \mathrm{KB}.\end{aligned}pairs/tilescalar ops/tileshared traffic/tile​=64×(64/2)=2048,≈2048×(4 mul+2 add)≈12,288,≈4096×2 bytes×2 (read+write)≈16 KB.​

12K scalar ops 相比 QK/PV 的 MMA FLOPs 看起来不大，这正是容易误判的地方。它小，但它发生在每个 selected tile 上；它用的不是 Tensor Core，而是 CUDA Core/SFU、LD/ST 和 shared memory；更重要的是它可能位于两个 Tensor Core GEMM 之间。因此“算力带宽比够”只能说明有理论空间，不能证明这段工作被隐藏。

当前 DSV4 的 Q-position inverse 更便宜，因为它只对最终输出的 RoPE 维做一次。decode 单 token 时，成本大致按 heads × rope_dim 算；own-position / relative value transform 则按 selected_kv × rope_dim 或 num_tiles × block × rope_dim 算。DSV4 报告还说明 RoPE 维以 BF16 存储，非 RoPE 维可 FP8，这会让 RoPE slice 的处理更像一条精度特殊的控制路径。[DSV4-Store]

5. 为什么常常需要 barrier：不是迷信同步，而是表示相位不同

如果只有一份 kv_shared，它在 QK 阶段的语义是 K 表示，例如 R(t)c_t；在 PV 阶段如果要 own-position inverse，它的语义要变成 value 表示，例如 c_t 或 R(t-q)c_t。同一 shared 地址在两个阶段代表不同东西，这就是 barrier 的来源。 

# hazard: one shared tile, two meanings
warp group 0: ldmatrix(kv_shared)     # QK still expects R(t)c_t
warp group 1: store(kv_shared)        # transform writes c_t
warp group 2: ldmatrix(kv_shared)     # PV expects c_t

CUDA 的 shared-memory matmul 示例会在写入 shared 后同步，再计算；也会在下一轮覆盖 shared 前同步，确保上一轮消费者已经读完。[CUDA-Matmul][CUDA-Sync] 这里同理：若要原地改写 tile，需要先确认所有 QK consumer 不再读旧表示，再确认 transform producer 已经写完新表示，PV consumer 才能读。

绕开 barrier 的方式怎么做新的代价
双 shared bufferkv_k_shared 给 QK，kv_v_shared 给 PVshared memory 占用增加，可能降低 occupancy；多一份写入和 bank traffic。
双 cache 表示cache 同时存 rotated key 和 de-rotated valueKV cache HBM 体积增加；paged cache、prefix cache、eviction 更复杂。
PV 重新读QK 读 rotated KV；PV 再从 HBM/L2 读 value-ready KV破坏 load once consume twice；decode 的 HBM/L2 压力上升。
warp specializationproducer warp 变换，consumer warp 做 MMA需要更细的 pipeline 状态；PV 仍要等当前 value-ready。

CUTLASS 对 Hopper warp-specialized GEMM 的描述很有参考意义：producer warp group 负责把 global memory 搬到 shared buffers，consumer warp group 等待 buffer filled 后发 MMA，再释放 buffer。[CUTLASS-Pipe] 这说明即使是最优化的 pipeline，也离不开清晰的 buffer 状态和同步语义。

6. 能不能算一部分 QK 就算这一部分 PV？可以，但账没消失

可以。FlashAttention 的核心就是按 K/V block 流式扫描，维护 running max 与 running sum，再把 partial output 合并。它不是先生成完整注意力矩阵，而是在线更新 softmax 统计量。[FA-Softmax] DSV4 本地 sparse kernel 也有同样结构：scores_max、scores_scale、sum_exp、acc_o 都在 tile loop 内更新。[Code-Kernel][vLLM]

m′=max⁡(m,max⁡jsj),ℓ′=ℓ em−m′+∑jesj−m′,O′=O em−m′+∑jesj−m′Vj.\begin{aligned}m' &= \max(m,\max_j s_j),\\ \ell' &= \ell\,e^{m-m'}+\sum_j e^{s_j-m'},\\ O' &= O\,e^{m-m'}+\sum_j e^{s_j-m'}V_j.\end{aligned}m′ℓ′O′​=max(m,jmax​sj​),=ℓem−m′+j∑​esj​−m′,=Oem−m′+j∑​esj​−m′Vj​.​

但 partial QK/PV 解决的是“不 materialize 全量 attention matrix”的问题，不自动解决“同一个 tile 的 K 表示何时可以改成 V 表示”的问题。只要 QK 的某些 MMA fragment 还会读某个 shared 地址，就不能把那个地址提前改写给 PV。

7. 把 K 现场 RoPE 和 DSV4 V 旋转放进同一张工程账本

下面这张表是本文的主账本。它故意不评价算法效果，只把推理 kernel 会付的资源列出来。

8. 结论：不是不能写，而是热路径值不值得改

从 kernel 可实现性看，raw-K 现场 RoPE、V own-position inverse、V relative rotate 都能写。手写 kernel 可以避免“寄存器一定翻倍”这种粗糙说法，也可以通过 fragment-level transform、双 buffer、warp specialization 或异步 pipeline 继续优化。

但工程代价的根子是：位置变换被搬进 per-KV tile 热循环后，会改变数据复用与依赖链。pre-RoPE K cache 把 K 做成 ready-to-dot；DSV4 当前 Q-position inverse 把 value 侧的相对旋转效果压到输出向量上。[RoPE][DSV4]这两者都避免在 QK/PV 之间改写 kv_shared。

更准确的一句话：问题不是 HBM 字节数是否翻倍，也不是 GPU 算不算得动旋转；问题是这个旋转若落在 QK/PV tile 的中间，就会消耗 CUDA Core、shared memory、register 和同步预算，并可能让 Tensor Core 等 value-ready。

所以你最开始的直觉“流式 kernel 技术上能实现、访存字节数可不涨”是对的；但它并不推出“工业 kernel 会无损采用”。工业实现更看重热循环里是否能维持简单的 buffer state、清晰的 producer/consumer 关系、稳定的 occupancy，以及能否让 Tensor Core 持续吃到已经准备好的 tile。
